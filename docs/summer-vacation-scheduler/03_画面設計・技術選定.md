## 1. 技術選定

### 1-1. 前提となる現状

このリポジトリは **ビルド不要の静的HTML/CSS/JSをVercelで配信**する構成
(ゲーム集と同じ方式)。夏休み調整アプリも同じ流儀で、
**1フォルダ追加するだけ**の形が最も保守しやすい。

ただし今回は「全員でデータを共有する」ため、ゲームと違って
**サーバー側のデータ保存**が必要になる。その保存先の選定が本フェーズの中心。

### 1-2. データ保存先の比較

| 案 | 構成 | 良い点 | 気になる点 |
|----|------|--------|-----------|
| **A. Vercel + Neon Postgres(推奨)** | 静的ページ + 同リポジトリ内のAPI(Vercel Functions)+ Neon(Vercelから数クリックで追加できる無料DB) | **新しいアカウント不要**(既存のVercelアカウントに追加するだけ)。接続情報は自動設定され、キーの手動コピーが不要。PINの照合をサーバー側で安全に行える | DBの中身を直接見る画面はやや簡素(通常運用では不要) |
| B. Supabase | 静的ページから Supabase(外部サービス)に直接読み書き | 管理画面が使いやすく、表計算感覚でデータを直せる | **新規アカウント作成が必要**。URLとキーを2つコピーして設定する手作業がある |
| C. Google スプレッドシート + GAS | シートをDB代わりにする | データが常にシートで見える | 20人同時アクセスに弱い。PIN保護や警告ロジックの実装が複雑化しやすい |

### 1-3. 推奨構成(案A)の全体像

```
利用者のスマホ/PC
   │  (URLにアクセス)
   ▼
Vercel ── natsuyasumi/index.html ほか(画面。静的ファイル)
   │
   ├── api/*.js(Vercel Functions = サーバー側の窓口)
   │     ・読み取り: カレンダー用データをまとめて返す
   │     ・書き込み: PINを照合してから本人の希望だけ更新
   │     ・警告判定・残り日数計算もここで実施
   ▼
Neon Postgres(データ保存。無料枠で十分: 20人×数百件程度)
```

**PINの守り方(F9 の実現方式)**
- PINはDBに**ハッシュ化して保存**(生のPINは保存しない)
- 希望の書き込みは必ず API 経由。APIがPINを照合し、**本人の希望以外は更新できない**
- 閲覧は誰でも可(URLを知っているメンバー向け。要件どおり)
- 位置づけは要件どおり「誤編集・なりすまし防止」レベル(銀行水準の認証ではない)

**ユーザーにお願いする作業(1回だけ、10分程度)**
1. Vercelで**新しいプロジェクトを作成**し、このGitリポジトリを選択
   - Root Directory を `natsuyasumi-app` に設定(ゲームとは別プロジェクトになる)
2. その新プロジェクトの Storage タブ → Create Database → **Neon (Postgres)** を選択して接続
   (これだけで接続情報が自動でこのプロジェクトに設定される)
3. 完了を私に伝える → 初期テーブル作成は私が用意するセットアップ処理で自動実行

※ フォルダ `natsuyasumi-app/` の中身(コード)は私が実装します。
  上記1でプロジェクトを作るのは中身ができてからでもOK(順番はPhase 3で案内します)。

## 2. データ設計

将来拡張「部>課>係」に備え、**組織は階層を持てるテーブル**として最初から設計する
(MVPでは課2件を入れるだけ)。

| テーブル | 列 | 備考 |
|----------|----|------|
| organizations | id, name, parent_id, kind(部/課/係) | parent_id で階層化。MVPでは `課A`, `課B` の2件(parent_id は空) |
| members | id, org_id, name, role(課長/係長/係員), pin_hash, display_order | 約20件 |
| leave_requests | id, member_id, date, status(◎/○/△/確定), memo | member_id+date で一意(1人1日1件) |
| events | id, org_id(空=全体), title, start_date, end_date | 業務予定 |
| settings | id, year, period_start, period_end, max_confirmed_days | 2026年は 7/1〜10/31、上限3日 |

**サーバー側で行う判定(APIの責務)**
- 残り日数 = 3 −(本人の「確定」件数)。確定が3件ある状態で4件目の確定はエラー
- 課長×係長警告 = 同じ課の課長と係長の両方に同日の休み(候補含む)がある日
- 在席0警告 = ある課の係員全員に同日の休み(候補含む)がある日(係員のみで判定)

## 3. 画面設計

画面は4つ。スマホは1カラム、PCはカレンダー+詳細の2カラム表示。

### S1: カレンダー画面(メイン・入口)

```
┌──────────────────────────────────┐
│ 🏖 夏休み調整 2026    [課A|課B|全員] │
│ わたし: 田中 ▼   残り 2/3日 [入力モード]│
├──────────────────────────────────┤
│ ◀ 8月 ▶   (7・8・9・10月を切替)      │
│ 月 火 水 木 金                       │
│ ┌────┬────┬────┬────┬────┐          │
│ │ 3  │ 4  │ 5📌│ 6  │ 7⚠ │          │
│ │●1  │    │    │◎1  │◎2  │          │
│ │◎2  │    │    │△2  │○1  │          │
│ └────┴────┴────┴────┴────┘          │
│ 凡例: ●確定 ◎絶対 ○できれば △候補     │
│       📌業務予定 ⚠要確認             │
└──────────────────────────────────┘
```
- マスには状態別の人数を集約表示。タップで S2(日別詳細)へ
- ⚠ は「課長×係長重複」「係員在席0」の日に表示
- 上部で課の絞り込み。「わたし」を選ぶと自分の希望が強調表示される

### S2: 日別詳細(下から出るシート / PCは右側に常設)

```
┌──────────────────────────────────┐
│ 8月7日(金)                    [×] │
│ ⚠ 課A: 課長と係長の休みが重なっています│
│    → 口頭で確認してください           │
├──────────────────────────────────┤
│ ● 確定   : 鈴木                    │
│ ◎ 絶対   : 田中(課長)・佐藤(係長)    │
│ ○ できれば: 高橋                    │
│ 📌 A社納品 締切(課A)               │
├──────────────────────────────────┤
│ [この日に自分の希望を入れる]          │
└──────────────────────────────────┘
```

### S3: 希望入力(入力モード)

```
┌──────────────────────────────────┐
│ 田中さんの入力  残り 2/3日      [終了]│
│ (はじめての時だけ) PIN: [＿＿＿＿]    │
├──────────────────────────────────┤
│ カレンダー上で日をタップするたびに切替: │
│   なし → △ → ○ → ◎ → なし          │
│ 長押し(またはボタン)で「●確定」に変更  │
│ ※確定は3日まで。超えるとエラー表示     │
│ メモ(任意): [子どもの行事      ]      │
└──────────────────────────────────┘
```
- PINは端末に記憶し、毎回の入力は不要にする(共有PCでは記憶しない選択も可)

### S4: 管理画面(当面は幹事役=言い出しっぺ用)

```
┌──────────────────────────────────┐
│ ⚙ 管理                            │
│ [メンバー] 名前/課/役職の一覧・追加・  │
│           削除・PIN再設定            │
│ [業務予定] 追加・編集・削除(課/全体)   │
│ [設定]    対象期間・上限日数          │
└──────────────────────────────────┘
```
- 管理画面は管理用PINで保護
- 将来拡張時は[メンバー]の上に[組織](部>課>係の追加・削除)が加わる

### 画面遷移

```
S1 カレンダー ─ 日をタップ → S2 日別詳細
   │  [入力モード] → S3 希望入力(PIN照合)
   └─ ⚙ → S4 管理(管理PIN)
```

## 4. 配置とURL(ゲームとは別で独立公開)

**方針**: 業務アプリのため、ゲーム集とは**別のサイト(別Vercelプロジェクト)として公開**する。
URL・ドメイン・アクセスがゲームと完全に分かれるので、業務用として扱いやすい。

### 構成(モノレポ内サブフォルダ → 独立プロジェクト)

- コードは同じGitリポジトリ内の独立フォルダ `natsuyasumi-app/` にまとめる
  ```
  natsuyasumi-app/
    public/        画面(index.html ほか静的ファイル)
    api/           サーバー側の窓口(Vercel Functions)
    vercel.json    このアプリ専用の設定
  ```
  → 既存のゲーム(リポジトリ直下の *.html / *.js)には**一切手を触れない**
- Vercel では**新しいプロジェクトをもう1つ作成**し、
  「Root Directory = `natsuyasumi-app`」に設定して、この branch(または main)から配信する
  - ゲーム集の既存プロジェクトとはデプロイ単位・URLが分離される
  - Neon DB もこの新プロジェクト側に接続する(ゲームとは無関係)

### URL

- 既定では新プロジェクトの Vercel URL(例: `https://natsuyasumi-app.vercel.app`)で公開
- 独自ドメイン/サブドメイン(例: `natsuyasumi.example.com`)を割り当てることも可能(任意・後からでOK)
- ゲーム選択のトップページには**リンクを追加しない**。URLはメンバーに直接共有する

> 補足: 「別リポジトリに完全に分ける」ことも可能ですが、当面は
> 1リポジトリ内で公開先だけ分ける上記方式が管理はシンプルです。
> 完全分離をご希望なら別リポジトリ化もできます。
