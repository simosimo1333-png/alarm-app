# 夏休み調整アプリ — 要件整理(Phase 1)

- 作成日: 2026-07-16
- ステータス: ドラフト(議論の過程で更新される前提)
- 目的: 企画書作成に向けて、現時点の要件・前提・未確定事項を整理する

---

## 1. 背景と課題

### 現状のやり方
- 空のカレンダーを印刷し、各自が手書きで夏休みの希望を記入している。

### 現状の課題
| 課題 | 具体的な困りごと |
|------|------------------|
| 見えづらい | 紙は1枚しかなく、その場に行かないと全体状況がわからない |
| 申請しづらい | 他の人の希望や業務予定が見えないため、遠慮したり出し直しになったりする |
| 共有できない | 紙のため、リモートや外出中のメンバーと状況を共有できない |
| 更新が大変 | 書き直し・消し込みが煩雑で、最新状態の維持にコストがかかる |

### なぜ取り組むのか
夏休みの調整状況が「見えづらく、申請しづらい」状態を解消し、
全員が全体を見ながら気持ちよく希望を出し合える状態をつくる。

---

## 2. ゴール

### 目的
夏休み(夏季休暇)の希望調整を、紙のカレンダーからアプリに置き換えて
**効率化・見える化・共有可能** にする。

### 成功基準(KPI)
- **数値的KPI**: 設定しない(現時点)
- **質的KPI**:
  - それぞれの大きな業務の予定が一覧できること
  - 各自の休みの希望が **希望の程度つき** で入力・閲覧できること
  - → 「この日は◎の人が2人いるな」「この週は繁忙だから避けよう」が一目でわかる状態

---

## 3. 利用者と利用シーン(確定事項)

ヒアリングにより以下が確定した。

| 項目 | 決定内容 |
|------|----------|
| 利用規模 | **2つの課**、各課 約10人(計 約20人) |
| 組織構造 | 各課に **課長1人・係長1人**、残りは **係員**(約8人) |
| 希望の程度 | **3段階**(例: ◎=絶対休みたい / ○=できれば休みたい / △=候補) |
| 確定の方法 | **全員で見ながら自主調整**(アプリは見える化まで。確定権限を持つ管理者は置かない) |
| 利用環境 | **スマホ・PC両方**(入力はスマホ、全体確認はPCなどの併用を想定) |
| 休暇のルール | **1人3日**、対象期間は **7月〜10月**。**残り日数は「確定」した休みだけを数える**(◎○△の候補は3日を超えて出してよい) |
| 体制のルール | **課長と係長が同じ日に休む場合は確認が必要**(アプリ上で警告表示)。**各課の係員は最低1人在席**すること |
| 編集権限 | **本人以外は希望を編集できない**。本人確認は **個人ごとの4桁PIN** で行う |

```
組織のイメージ:
  課A ─ 課長(1) ─ 係長(1) ─ 係員(約8)
  課B ─ 課長(1) ─ 係長(1) ─ 係員(約8)
```
※ 課長×係長の警告は**同じ課の中で判定**する(課をまたぐ組み合わせは対象外)— 2026-07-16 確定。

### 想定される利用の流れ(To-Be ワークフロー)
1. カレンダー(対象期間: 7月〜10月)をアプリ上に用意する
2. 各メンバーが自分のスマホ/PCから、休みたい日に ◎○△ を入力する(候補は3日を超えて出してよい)
3. 大きな業務予定(締切・イベント・繁忙日など)もカレンダー上に登録する
4. 全員が同じカレンダーを見て、重なり・業務予定・警告(課長×係長の重複、係員の在席0人)を確認しながら自主的に調整する
5. 警告が出ている日は、当事者間・上長と口頭で確認したうえで調整する
6. 調整がついた日を各自が「確定」にする(確定は合計3日まで。確定した分だけ残り日数が減る)

### 得られる価値
- いつでもどこでも最新の調整状況が見える(紙の場所に行かなくてよい)
- 希望の「程度」が見えるので、譲り合い・調整の会話がしやすくなる
- 業務予定と休み希望を同じ画面で見られるので、判断が速くなる

## 4. MVP 機能要件(案)

### 必須(これがないと紙の代替にならない)
| # | 機能 | 内容 |
|---|------|------|
| F1 | カレンダー表示 | 対象期間(7月〜10月)を月表示。全員の希望と業務予定を重ねて表示 |
| F2 | 休み希望の入力 | 日を選んで ◎○△ の3段階で入力。自分の希望はいつでも変更可能 |
| F3 | メンバー・課 | 約20人を2つの課に分けて登録(役職: 課長/係長/係員)。課で絞り込み表示できる |
| F4 | 業務予定の登録 | 大きな業務予定(締切・イベント等)を誰でも登録でき、カレンダーに表示 |
| F5 | 共有 | URL を知っているメンバー全員が同じ画面を見られる |
| F6 | マルチデバイス | スマホ・PC どちらでも入力・閲覧できる(レスポンシブ対応) |
| F7 | 残り日数の表示 | 1人3日の枠に対し、**確定した日数**を自動集計して残り日数を表示 |
| F8 | ルール警告 | ①同じ課の課長と係長が同日に休む日、②課の係員の在席が0人になる日を、カレンダー上で警告表示 |
| F9 | 本人のみ編集 | 個人ごとの4桁PINにより、自分の希望だけを編集できるようにする |
| F10 | 確定マーク | 調整がついた休みを本人が「確定」にする。確定は合計3日まで(超過は登録不可)。◎○△の候補と区別して表示 |

### あると良い(MVP に入れるか要議論)
| # | 機能 | 内容 |
|---|------|------|
| F11 | 日別サマリー | ある日をタップすると「誰が◎/○/△/確定か」「業務予定」「警告の有無」が一覧できる |
| F12 | 希望の理由メモ | 「子どもの行事」などの短いコメントを希望に添えられる |

### MVP の対象外(候補 — 要確認)
- 組織階層の管理機能(部>課>係の追加・削除)→ **将来拡張**として下記に記載
- 本格的なID・パスワード管理(F9 は個人PINなどの簡易認証で代替する想定)
- 承認ワークフロー(申請→上長承認のような機能。「自主調整」方針のため、課長×係長の重複も承認ではなく警告表示+口頭確認とする)
- 通知機能(メール・プッシュ通知)
- 夏休み以外の休暇(有休全般)への対応 → まずは夏休み専用
- 勤怠システム連携・出力

### 将来拡張(MVP完成後に対応 — 2026-07-16 追加)
- **組織階層の管理**: 部を最上位とした「**部 > 課 > 係**」の階層で、組織を追加・削除できるようにする
  - MVP では「課2つ」を初期データとして登録するだけにとどめるが、**課の情報をプログラムに直書きせず「組織」データとして持たせておく**(Phase 2 の設計で考慮。後から階層を足しやすくするため)
  - 階層導入時に再検討すること:
    - 「最低1人在席」の判定単位を課から**係単位**に変えるか
    - 警告ルール(課長×係長など)を階層・役職ごとに設定できるようにするか
    - 組織の追加・削除を誰ができるか(管理者権限の導入)

## 5. 画面イメージ(ラフ)

```
┌─────────────────────────────────────┐
│ 夏休み調整 2026          [課A|課B|全員]  │
├─────────────────────────────────────┤
│  ◀ 2026年8月 ▶      (対象: 7月〜10月)  │
│ ┌───┬───┬───┬───┬───┬───┬───┐        │
│ │日 │月 │火 │水 │木 │金 │土 │        │
│ ├───┼───┼───┼───┼───┼───┼───┤        │
│ │   │ 3 │ 4 │ 5 │ 6 │ 7 │   │        │
│ │   │◎2 │   │📌締切│◎1 │⚠○3│   │      │
│ │   │○1 │   │   │△2 │   │   │        │
│ └───┴───┴───┴───┴───┴───┴───┘        │
│  8/7 の詳細:  ⚠ 課長と係長が重複       │
│   ◎ 田中(課長)・佐藤(係長)  ○ 鈴木     │
│   📌 A社納品 締切                     │
├─────────────────────────────────────┤
│ [自分の希望を入力] 田中さん 残り 2/3日  │
└─────────────────────────────────────┘
```

- カレンダーのマスには「◎○△ の人数」と業務予定(📌)、警告(⚠)を集約表示
- 日をタップ/クリックすると誰の希望か・警告の理由が見える(F11)
- 入力モードでは PIN で本人確認のうえ、日をタップして ◎→○→△→なし を切り替え(F9)
- 調整がついた日は「確定」に切り替える。確定した休みは色を変えて表示(F10)
- 入力エリアに残り日数(例: 残り 2/3日 — 確定ベース)を常時表示(F7)

## 6. データの考え方(概要)

| データ | 主な項目 |
|--------|----------|
| メンバー | 名前、所属課(A/B)、役職(課長/係長/係員)、本人確認用PIN(4桁) |
| 休み希望 | メンバー、日付、状態(◎/○/△/**確定**)、(メモ) |
| 業務予定 | 日付(または期間)、タイトル、対象(課A/課B/全体) |
| 設定 | 対象期間(2026年は 7/1〜10/31)、1人あたりの確定上限(3日) |

### ルール判定(F7・F8・F10 の裏側)
- **残り日数** = 3日 −(本人の「確定」日数)。◎○△の候補は数えない
- **確定の上限** = 確定は合計3日まで。4日目を確定しようとしたらエラーにする
- **課長×係長 警告** = 同じ課の課長と係長の両方に、同じ日の休み(候補または確定)がある
- **在席0人 警告** = ある課の係員全員に、同じ日の休み(候補または確定)がある(課ごとに、係員のみで判定)

※ 全員で共有するため、データはブラウザ内保存ではなく **サーバー側に保存** が必要。
実装方式(どのサービスを使うか)は Phase 2 の技術選定で決める。
※ 将来の「部>課>係」階層化(4章の将来拡張を参照)に備え、課をプログラムに固定せず
「組織」データとして持たせる。MVP時点の中身は課A・課Bの2件のみ。

## 7. 未確定事項(次に決めたいこと)

解決済みの論点(2026-07-16 確定):
- 対象期間=7月〜10月、日数=1人3日
- 組織=2つの課、各課に課長1・係長1・係員約8。課長×係長の同日休みは要確認、各課の係員は最低1人在席
- 残り日数=**確定した休みだけを数える**(候補◎○△は3日を超えて出してよい)→ 確定マーク(F10)を MVP 必須に昇格
- 本人確認=個人ごとの4桁PIN
- 課長×係長の警告は**同じ課の中で判定**(課をまたぐ組み合わせは対象外)
- 組織階層の管理(部>課>係)は**将来拡張**とし、MVP には含めない(データ設計だけ備える)

| # | 論点 | 選択肢の例 / 推奨案 |
|---|------|---------------------|
| Q1 | メンバーの初期登録は誰がするか | **推奨: 言い出しっぺ(あなた)が最初に20人分の名前・課・役職を一括登録し、PINを各自に配る**。以降の変更も同じ人が担当 |
| Q2 | 業務予定は課単位か全体か | 課ごとに色分け表示するか、全体共通でよいか |
| Q3 | 社外からのアクセス | 自宅・移動中からも使うか(URL共有のセキュリティ方針、業務情報をどこまで載せるかに影響) |
