# 夏休み調整アプリ — 要件整理(Phase 1)

- 作成日: 2026-07-16
- ステータス: ドラフト(議論の過程で更新される前提)
- 目的: 企画書作成に向けて、現時点の要件・前提・未確定事項を整理する

---

## 1. 背景と課題

### 現状のやり方
- 空のカレンダーを印刷し、各自が手書きで夏休みの希望を記入している。

### 現状の課題
| 課題 | 具体的な困りごと |
|------|------------------|
| 見えづらい | 紙は1枚しかなく、その場に行かないと全体状況がわからない |
| 申請しづらい | 他の人の希望や業務予定が見えないため、遠慮したり出し直しになったりする |
| 共有できない | 紙のため、リモートや外出中のメンバーと状況を共有できない |
| 更新が大変 | 書き直し・消し込みが煩雑で、最新状態の維持にコストがかかる |

### なぜ取り組むのか
夏休みの調整状況が「見えづらく、申請しづらい」状態を解消し、
全員が全体を見ながら気持ちよく希望を出し合える状態をつくる。

---

## 2. ゴール

### 目的
夏休み(夏季休暇)の希望調整を、紙のカレンダーからアプリに置き換えて
**効率化・見える化・共有可能** にする。

### 成功基準(KPI)
- **数値的KPI**: 設定しない(現時点)
- **質的KPI**:
  - それぞれの大きな業務の予定が一覧できること
  - 各自の休みの希望が **希望の程度つき** で入力・閲覧できること
  - → 「この日は◎の人が2人いるな」「この週は繁忙だから避けよう」が一目でわかる状態

---

## 3. 利用者と利用シーン(確定事項)

ヒアリングにより以下が確定した。

| 項目 | 決定内容 |
|------|----------|
| 利用規模 | **約10人のチーム × 2チーム**(計 約20人) |
| 希望の程度 | **3段階**(例: ◎=絶対休みたい / ○=できれば休みたい / △=候補) |
| 確定の方法 | **全員で見ながら自主調整**(アプリは見える化まで。確定権限を持つ管理者は置かない) |
| 利用環境 | **スマホ・PC両方**(入力はスマホ、全体確認はPCなどの併用を想定) |
| 休暇のルール | **1人3日**、対象期間は **7月〜10月**。使用日数(残り日数)を管理する |
| 体制のルール | **課長と係長が同時に休む日は確認が必要**(アプリ上で警告表示)。**係には最低1人は残る**こと |
| 編集権限 | **本人以外は希望を編集できない**(なりすまし・誤編集の防止) |

### 想定される利用の流れ(To-Be ワークフロー)
1. カレンダー(対象期間: 7月〜10月)をアプリ上に用意する
2. 各メンバーが自分のスマホ/PCから、休みたい日に ◎○△ を入力する(1人3日の枠。残り日数が見える)
3. 大きな業務予定(締切・イベント・繁忙日など)もカレンダー上に登録する
4. 全員が同じカレンダーを見て、重なり・業務予定・警告(課長×係長の重複、係の在席0人)を確認しながら自主的に調整する
5. 警告が出ている日は、当事者間・上長と口頭で確認したうえで調整する
6. 調整がついたら各自が希望を「確定」状態に更新する(※確定の扱いは要議論)

### 得られる価値
- いつでもどこでも最新の調整状況が見える(紙の場所に行かなくてよい)
- 希望の「程度」が見えるので、譲り合い・調整の会話がしやすくなる
- 業務予定と休み希望を同じ画面で見られるので、判断が速くなる

## 4. MVP 機能要件(案)

### 必須(これがないと紙の代替にならない)
| # | 機能 | 内容 |
|---|------|------|
| F1 | カレンダー表示 | 対象期間(7月〜10月)を月表示。全員の希望と業務予定を重ねて表示 |
| F2 | 休み希望の入力 | 日を選んで ◎○△ の3段階で入力。自分の希望はいつでも変更可能 |
| F3 | メンバー・チーム | 約20人を2チームに分けて登録。チームで絞り込み表示できる |
| F4 | 業務予定の登録 | 大きな業務予定(締切・イベント等)を誰でも登録でき、カレンダーに表示 |
| F5 | 共有 | URL を知っているメンバー全員が同じ画面を見られる |
| F6 | マルチデバイス | スマホ・PC どちらでも入力・閲覧できる(レスポンシブ対応) |
| F7 | 残り日数の表示 | 1人3日の枠に対し、各自の使用予定日数・残り日数を自動集計して表示 |
| F8 | ルール警告 | ①課長と係長が同日に休む日、②係の在席が0人になる日を、カレンダー上で警告表示 |
| F9 | 本人のみ編集 | 簡易認証(個人PINなど)により、自分の希望だけを編集できるようにする |

### あると良い(MVP に入れるか要議論)
| # | 機能 | 内容 |
|---|------|------|
| F10 | 日別サマリー | ある日をタップすると「誰が◎/○/△か」「業務予定」「警告の有無」が一覧できる |
| F11 | 希望の理由メモ | 「子どもの行事」などの短いコメントを希望に添えられる |
| F12 | 確定マーク | 調整がついた休みを「確定」として区別表示する(残り日数の計算対象を確定分に絞れる) |

### MVP の対象外(候補 — 要確認)
- 本格的なID・パスワード管理(F9 は個人PINなどの簡易認証で代替する想定)
- 承認ワークフロー(申請→上長承認のような機能。「自主調整」方針のため、課長×係長の重複も承認ではなく警告表示+口頭確認とする)
- 通知機能(メール・プッシュ通知)
- 夏休み以外の休暇(有休全般)への対応 → まずは夏休み専用
- 勤怠システム連携・出力

## 5. 画面イメージ(ラフ)

```
┌─────────────────────────────────────┐
│ 夏休み調整 2026        [チームA|チームB|全員] │
├─────────────────────────────────────┤
│  ◀ 2026年8月 ▶      (対象: 7月〜10月)  │
│ ┌───┬───┬───┬───┬───┬───┬───┐        │
│ │日 │月 │火 │水 │木 │金 │土 │        │
│ ├───┼───┼───┼───┼───┼───┼───┤        │
│ │   │ 3 │ 4 │ 5 │ 6 │ 7 │   │        │
│ │   │◎2 │   │📌締切│◎1 │⚠○3│   │      │
│ │   │○1 │   │   │△2 │   │   │        │
│ └───┴───┴───┴───┴───┴───┴───┘        │
│  8/7 の詳細:  ⚠ 課長と係長が重複       │
│   ◎ 田中(課長)・佐藤(係長)  ○ 鈴木     │
│   📌 A社納品 締切                     │
├─────────────────────────────────────┤
│ [自分の希望を入力] 田中さん 残り 2/3日  │
└─────────────────────────────────────┘
```

- カレンダーのマスには「◎○△ の人数」と業務予定(📌)、警告(⚠)を集約表示
- 日をタップ/クリックすると誰の希望か・警告の理由が見える(F10)
- 入力モードでは PIN で本人確認のうえ、日をタップして ◎→○→△→なし を切り替え(F9)
- 入力エリアに残り日数(例: 残り 2/3日)を常時表示(F7)

## 6. データの考え方(概要)

| データ | 主な項目 |
|--------|----------|
| メンバー | 名前、所属する係(A/B)、役職(課長/係長/一般)、本人確認用PIN |
| 休み希望 | メンバー、日付、程度(◎/○/△)、(メモ)、(確定フラグ) |
| 業務予定 | 日付(または期間)、タイトル、対象(係A/係B/全体) |
| 設定 | 対象期間(2026年は 7/1〜10/31)、1人あたりの日数上限(3日) |

### ルール判定(F7・F8 の裏側)
- **残り日数** = 3日 −(本人が入力した休み日数)※◎○△のどれを数えるかは Q2 参照
- **課長×係長 警告** = 同じ日に課長と係長の両方に休み希望がある
- **在席0人 警告** = 同じ日に、ある係のメンバー全員に休み希望がある(係ごとに判定)

※ 全員で共有するため、データはブラウザ内保存ではなく **サーバー側に保存** が必要。
実装方式(どのサービスを使うか)は Phase 2 の技術選定で決める。

## 7. 未確定事項(次に決めたいこと)

解決済みの論点(2026-07-16 確定): 対象期間=7月〜10月、日数=1人3日、
体制ルール=課長×係長の重複は要確認・係は最低1人残る、編集=本人のみ。

| # | 論点 | 選択肢の例 |
|---|------|-----------|
| Q1 | 体制の構造の確認 | 「係」=2つのチームのことか? 課長・係長は各係に1人ずつか、課長は全体で1人か |
| Q2 | 残り日数のカウント方法 | ◎○△すべてを3日枠に数えるか / 確定した休みだけ数えるか(候補は多めに出せる方が調整しやすい) |
| Q3 | 本人確認の方式 | 個人PIN(4桁)を想定 / 合言葉 / 個人ごとの専用URL。どこまで厳密にするか |
| Q4 | メンバー登録は誰がするか | 管理者役が最初に一括登録(役職・係・PINの設定が必要なため、こちらを推奨) / 各自が追加 |
| Q5 | 業務予定は係単位か全体か | 係ごとに色分け表示するか |
| Q6 | 「確定」の扱い | 確定マーク(F12)を MVP に入れるか、運用でカバーするか(Q2 の答えに影響) |
| Q7 | 社外からのアクセス | 自宅・移動中からも使うか(URL 共有のセキュリティ方針に影響) |
